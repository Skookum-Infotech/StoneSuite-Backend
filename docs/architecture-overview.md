## The shape of the system

A Go backend for a **multi-tenant, white-label CRM/ERP**, built on
**database-per-tenant** isolation. There is one control-plane database holding
tenants and login identities, and one physically separate database per customer
organisation holding all of their business data.

That choice drives nearly everything else: there are no `WHERE tenant_id`
filters anywhere, because the database connection *is* the tenancy boundary. A
query cannot leak across tenants by forgetting a clause; it would have to open
the wrong pool.

```
Request
  │
  ├─ RequestLogger ──── request id, one log line per response
  ├─ Recover ────────── a panic never takes the process down
  ├─ corsHandler ────── ⚠️ also a prefix allowlist; see "Two routers" below
  │
  ├─ RequireAuth ────── verifies the JWT, extracts identity/tenant/kind
  │                     and confines portal tokens to /api/portal/
  ├─ RateLimiter ────── per-IP for credentials, per-tenant for everything else
  ├─ TenantResolver ─── control-plane lookup → this tenant's *pgxpool.Pool*
  │
  └─ Handler ────────── authz.Check(resource, action) → scope → store
```

**Numbers, as of this commit:** 462 endpoints across 7 surfaces · 179 tenant
tables · 15 control-plane tables · 43 RBAC resources · ~35 tenant modules.

| Surface | Endpoints | Who calls it |
|---|---:|---|
| `/api/tenant/*` | 396 | The staff application. JWT + resolved tenant database. |
| `/api/portal/*` | 25 | Customer portal (see below). |
| `/api/auth/*` | 16 | Staff sign-in, session rotation, SAML SSO. |
| `/api/platform/*` | 8 | Platform-admin operations across tenants. |
| `/api/onboarding/*` | 7 | Public tenant onboarding and staff invitations. |
| `/api/customer/*` | 4 | A second customer surface (see below). |

**37 endpoints require no credential at all.** They are enumerated in
`api-reference.md` and pinned by a test — adding one is a deliberate, reviewed
act rather than something that arrives with a feature.

## Authorization, in three layers

1. **Authentication** — an HS256 JWT carrying `identity_id`, `tenant_id` and,
   for customers, `kind=portal`. Staff tokens carry no `kind` claim, so absence
   means staff and every token minted before the portal existed still works.
2. **Permission** — `authz.Check(resource, action)` against a 43-resource
   catalog. Grants live in the tenant's own `roles` / `role_permissions` /
   `user_roles` tables, so each workspace defines its own roles.
3. **Scope** — `all` or `own`, resolved with the permission. List endpoints push
   the scope into SQL; single-record endpoints call `recordInScope`. **Scope
   denial returns 404, not 403**, so record ids cannot be enumerated by
   probing.

The scope model is two-level and fail-closed: anything unrecognised narrows to
`own`. A caller with no employee profile owns nothing and gets an empty page,
which is the correct failure direction.

## Business modules

Roughly 35 modules, largest first: **inventory** (79 endpoints — items, units,
bins, bundles, warehouses, adjustments, transfers, cycle counts), **finance**
(38 — chart of accounts, journals, cash transfers, accounting periods), **CRM**
(23 — the lead → prospect → customer pipeline), **fabrication** (19), and the
document chain:

```
estimate → quote → sales order → invoice → payment
                                    └──────→ credit memo → refund
                    sales order → fabrication job
```

Purchasing mirrors it: requisition → purchase order → item receipt → vendor
bill → vendor payment / vendor credit.

**These modules are structural copy-paste twins.** There is no shared base
class: each has its own package, its own tables, its own controller and its own
RBAC entries, cloned from a skeleton. A cross-cutting fix must be hand-ported to
every one — the `module-drift-checker` agent exists precisely because that is
easy to get wrong.

## ⚠️ Two customer portals

**The system currently has two independent, overlapping customer-portal
implementations.** Both are live. This is the most significant thing in this
document.

| | `/api/portal/*` (PR #131) | `/api/customer/*` (PR #140) |
|---|---|---|
| Identity store | `identities` + `identity_tenants` | `customer_identities` (own table) |
| Logins per customer | many | **one** (`UNIQUE (customer_id)`) |
| Multi-workspace | yes — one login, several tenants, in-session switcher | no |
| JWT discriminator | `kind=portal` | `principal_type=customer` |
| Invitations | `portal_invites`, config-driven expiry, resend | inline token on the identity row, 48h fixed |
| Password reset | yes | no |
| Reads | sales orders, invoices, payments, refunds | none |
| Writes | messages on documents, own profile | notes |
| Endpoints | 25 | 4 |

They do not share a table, a token format, or a middleware. Both mint
customer-facing sessions against the same `customer` records.

**Why it matters beyond tidiness:**

- Two auth surfaces mean two places to get customer authorization right, and two
  places to patch when something is found wrong in one of them.
- A customer could plausibly hold credentials in both, with different passwords
  and different reset paths.
- `/api/customer/*` was **completely unreachable** from the day it merged until
  this commit — 404'd by the allowlist described below — so it has never run in
  production and is effectively untested against real traffic.

**Recommendation: consolidate onto one.** No decision is made here; the point is
that having two is a choice the team should make explicitly rather than inherit.
If `/api/portal/*` wins, `/api/customer/*` and `customer_identities` need a
deprecation path. If `/api/customer/*` wins, it needs the multi-workspace
support, invitations and document access the other already has.

## ⚠️ Two routers

`main.go` decides reachability in **two** places, hundreds of lines apart:

1. `ServeMux` — which handler serves a path.
2. A prefix allowlist inside `corsHandler` — which paths are allowed to reach
   the mux at all. Anything outside it gets `{"success":false,"message":"API
   route not found."}` before routing happens.

A route can be registered perfectly and still be dead in production, with no
compile error and nothing in the diff to notice. This has now happened twice:
`/api/portal/*` when the portal landed, and `/api/customer/*`, which shipped
dead and stayed dead across several releases until it was found while writing
these docs.

`TestEveryRegisteredRouteIsReachable` now fails the build if it recurs. The
underlying design smell — two sources of truth for routing — is worth removing,
but that is a larger change than this one deserved.

## Cross-cutting infrastructure

- **Record filter engine** (`query/`) — the single store-agnostic path for
  filtering, sorting and keyset pagination. Field keys are whitelisted
  (unresolved → 400, never raw SQL), values are always parameterised, and the
  user's filter is **ANDed** onto the caller's scope clause so it can only ever
  narrow. Pagination is keyset with opaque cursors — there is no offset and no
  total count anywhere in the API.
- **AI / RAG** (`ai/`) — provider-agnostic embeddings + LLM, self-hosted via
  Ollama as its own Fly app. Chosen for data residency, not cost.
- **Provisioning** (`provisioning/`, `jobqueue/`) — creating a tenant means
  creating a database, applying the schema, seeding RBAC and workflows, and
  making an R2 bucket. Runs as resumable async jobs.
- **Storage** (`storage/`) — per-tenant Cloudflare R2 buckets, presigned URLs.
- **Observability** — structured `slog` only, Prometheus at `/api/metrics`,
  optional Sentry and Axiom shipping. Security events use a stable
  `security_event` key so denials are greppable.

## Migrations

Two canonical, **idempotent** SQL files re-applied on every boot — there are no
numbered migration files. Columns are added with `ADD COLUMN IF NOT EXISTS`;
tables with `CREATE TABLE IF NOT EXISTS`. `DROP`, `TRUNCATE`, renames and
down-migrations are forbidden; recovery is Neon point-in-time restore.

The practical consequence for a reviewer: **never edit an existing `CREATE
TABLE` body to add a column.** `CREATE TABLE IF NOT EXISTS` is a no-op on every
existing tenant, so the column would reach only fresh databases and diverge
permanently.

## Regenerating this documentation

```bash
go run ./cmd/gen-apidocs          # rewrite the generated artifacts
go run ./cmd/gen-apidocs -check   # fail if they are stale (what CI runs)
```

The generator parses `main.go` with `go/ast` rather than regex, so it cannot
silently miss a registration. It deliberately does **not** model request or
response bodies: Go handlers decode into anonymous structs, and a half-guessed
schema is worse than an honest omission. What it guarantees completely is the
endpoint list and the credential each one demands.

If it reports a route using an unrecognised middleware chain, it **fails rather
than guessing** — add the chain to `chainAuth` in
`cmd/gen-apidocs/classify.go`. Guessing would publish a wrong claim about
whether an endpoint is public.
